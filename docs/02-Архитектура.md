## Стек

- **Vite + React + TypeScript**, `strict` и `noUncheckedIndexedAccess`. Проект идёт через много сессий, и без типов модель расползётся между ними
- Роутинг через хеш (`#/today`), библиотека `react-router-dom`, `HashRouter` — на GitHub Pages обычные пути дают 404 при обновлении страницы
- Сайт живёт по `/DeluVremya/`, а не в корне домена: `base` в `vite.config.ts` равен имени репозитория. С ним же согласованы `start_url`, `scope`, `id` манифеста и пути иконок. Неверный `base` даёт зелёную сборку и белую страницу — диагностируется плохо, лечится одной строкой
- Стили обычным CSS, без Tailwind
- Хранилище на устройстве — IndexedDB
- Service worker свой, собирается `injectManifest` — иначе в него не положить код напоминаний. Точка входа — `src/sw.ts`, сам работник — ядра (`startWorker`)
- В манифесте **`share_target` и `shortcuts`** (Р-09). Это не украшение, а главный путь ввода
- **Ядро семьи — `FamilyCore`**, подмодулем git в `src/shared` (Р-83): хранение, синхронизация, импорт, общие экраны, работник, каркас стилей и сборки. Приложение отдаёт ему свой конфиг `AppConfig`
- Бэкенда нет

## Два репозитория

| Репозиторий | Что внутри | Видимость |
|---|---|---|
| `DeluVremya` | исходники, сборка, GitHub Pages | публичный |
| `FamilyCore` | ядро семьи, подмодулем в `src/shared` | публичный |
| Данные | JSON-файлы с записями | приватный |

Pages для приватного репозитория требуют платного тарифа, поэтому код публичный. Секретов в нём нет по определению. Токен вводится руками в настройках и живёт только в браузере.

## Модель данных

Две категории сущностей: **справочники** (чем пользуемся) и **записи** (что было или задумано).

### Общая часть

```ts
type Base = {
  id: string          // ULID, генерируется локально, сортируется по времени
  updatedAt: string   // ISO 8601, время последнего изменения записи
  deleted?: boolean   // метка удаления, не вычищается никогда
}
```

Та же `Base`, что у всей семьи: она — часть **договора семьи** и живёт в ядре, `FamilyCore`, `core/model.ts`; описание договора — там же, `docs/02-Архитектура.md`, «Договор семьи». Здесь не переопределяется: правка договора — решение ядра и релиз на все приложения сразу.

### Справочники

```ts
// Категория учёта времени: Зарядка, Шахматы, Чтение, Ютуб, Прогулка, Прочее…
type Category = Base & {
  name: string
  order: number                // порядок на экране дня и в сводках
  kind: 'useful' | 'neutral' | 'idle'   // признак для обзора недели, не для дневного экрана (Р-05)
  archived?: boolean
  group?: string               // группа: кнопки и итоги по группам (Р-81)
  movedTo?: string             // у надгробия: куда перенесены её блоки (Р-22, Р-29)
  norm?: {                     // норма недели (Р-45); все поля необязательны
    minDays?: number           //   дней с блоком — не меньше
    minMinutes?: number        //   минут — не меньше
    maxMinutes?: number        //   минут — не больше
    since?: string             //   YYYY-MM-DD, с какого дня считается история (Р-53, Р-56)
  }
}

// Пресет — кнопка «Чтение +30». Заводится с экрана категории.
type Preset = Base & {
  categoryId: string
  minutes: number
  order: number
}

// Шаблон дня: «рабочий», «выходной». Порождает записи плана на конкретный день.
type DayTemplate = Base & {
  name: string
  items: { title: string; estMin?: number; main?: boolean }[]
  order: number
}
```

### Записи

```ts
// Одна сущность на входящее, дело, наблюдение, замысел и пункт плана дня (Р-09, Р-31).
type Note = Base & {
  text: string
  kind: NoteKind               // 'task' | 'thought' | 'goal'
  capturedOn: string | null    // YYYY-MM-DD, когда записана; null → дата неизвестна (Р-08)
  plannedFor: string | null    // YYYY-MM-DD, на какой день поставлена; null → лежит во входящих
  main?: boolean               // главное дело того дня, на который поставлена
  order?: number               // место пункта в своём дне; нет — после упорядоченных, по id (Р-75)
  estMin?: number              // оценка длительности, для реализма плана
  status: NoteStatus           // 'open' | 'done' | 'someday' | 'dropped'
  doneOn?: string              // YYYY-MM-DD, когда выполнено
  refs?: string[]
}

type NoteKind = 'task' | 'thought' | 'goal'
type NoteStatus = 'open' | 'done' | 'someday' | 'dropped'

// Блок учтённого времени.
type TimeBlock = Base & {
  date: string                 // YYYY-MM-DD, дата события, не дата ввода
  categoryId: string
  minutes: number
  bgCategoryId?: string        // фоновая активность: покер под ютуб
  note?: string
  refs?: string[]
}

// Проведённый обзор недели. id — `review:<weekStart>`: один обзор на неделю (Р-42).
type Review = Base & {
  weekStart: string            // YYYY-MM-DD, понедельник недели
  doneAt: string               // ISO 8601, когда обзор провели
  note?: string                // не используется: наблюдение недели — мысль (Р-49)
  refs?: string[]              // `note:<id>` — наблюдение недели
}

// Вид записи. Три значения — ровно то, что описано выше.
type RecordKind = 'note' | 'time' | 'review'
```

### Заметки по модели

- **Входящее, дело, наблюдение, замысел и пункт плана — одна структура** (Р-09). Входящее — `plannedFor: null`; пункт плана — дата проставлена; наблюдение — `kind: 'thought'`; замысел — `kind: 'goal'` (Р-31). Переход между состояниями это правка двух полей, а не превращение одной сущности в другую
- **Замысел — большая цель без конкретного шага**: «выучить английский». В неразобранное и в разбор висяков не попадает — у него свой блок. Дело относится к замыслу строкой `note:<id замысла>` в `refs`, одно дело — один замысел. Иерархии глубже нет (Р-03)
- **`capturedOn` и `plannedFor` — разные вещи.** Первое отвечает на «когда записана» и кормит возврат наблюдений, второе — на «на какой день поставлена». Мысль, записанная в марте и поднятая в плане в июне, сохраняет оба
- **`estMin` необязательна.** Реализм плана считается по тем пунктам, у которых она есть, и всегда называет, сколько пунктов в счёт не вошло. Число идёт с основанием
- **Привычки своей сущности не имеют** (Р-03). Шаблон дня порождает обычные `Note` на конкретный день; выполнение привычки — обычный `status: 'done'`
- **Пункт плана** — живая заметка с `plannedFor` этого дня, открытая или сделанная. Перенос на другой день и возврат во входящие — правка `plannedFor`, и оба снимают `main`: главное выбирается на свой день (Р-34). Открытый пункт прошедшего дня ждёт решения в блоке «С прошлых дней», пока его не перенесут, не вернут или не закроют
- **Порядок пунктов дня — `order`** (Р-75): с полем — по нему, без поля — после, по `id`. Перенос и возврат снимают `order`, как и `main`
- **Главное дело — одно на день** (Р-07). Отметка снимает `main` с прежнего пункта дня. Если после обмена устройств отмечены два, главным считается позднее по `updatedAt`; в базу это не пишется (Р-40)
- **Реализм** — сумма `estMin` открытых пунктов сегодняшнего плана против остатка окна дня учёта (Р-21) до его конца, с числом пунктов без оценки (Р-35). Обязательства — работа, дорога — пунктами плана с оценкой
- **Шаблон применяется без дублей**: пункт, чей текст уже стоит в этот день — регистр, «ё» и лишние пробелы не в счёт, как в поиске, — не ставится; `main` из шаблона — только если у дня главного нет. `capturedOn` порождённого пункта — день применения (Р-39)
- **Фоновая активность — поле, а не вторая запись.** Одна запись описывает «час ютуба, под него покер»; сумма по основной категории не удваивается
- **`refs` — связи между записями** и, позже, между приложениями семьи. Строка ссылки начинается с вида записи: `note:<id>`. Первое применение — дело и его замысел (Р-31)
- **`kind` категории существует, но на дневном экране не красит** (Р-05). Признак нужен обзору недели, где смотрят на неделю целиком
- **Группа категории — строка `group`** (Р-81), своей записи у группы нет. Одинаковые названия без учёта регистра, «ё» и пробелов — одна группа. Порядок групп — по первой их категории в общем `order`; без группы — в конце. Группа раскладывает кнопки и строки итогов, признак `kind` — для обзора: это две разные классификации
- **Id категории — из названия**, `cat:<название>`: одно название на двух устройствах — одна запись. **Дубль после встречного переименования сливается сам** после прихода данных (Р-29): остаётся id, совпадающий с названием, содержимое — от поздней правки. Надгробие хранит `movedTo`, и блок, приехавший к нему позже, переходит по нему
- **Id обзора — из недели**, `review:<понедельник>` (Р-42): второе проведение той же недели — правка той же записи, и два устройства не заведут два обзора. Категории и обзоры — два исключения из «id — ULID»
- **Норма недели — поле категории** (Р-45). «Раз» — день, в котором у категории есть блок. Считается, как и итоги периода, по основной категории; фоновое — отдельной строкой и в сумму не входит (Р-43)
- **История нормы — с `since`** (Р-53, Р-56): день первого сохранения нормы, правка правил его не сдвигает; нет поля — день последней правки категории. В счёт — полные недели с понедельника не раньше `since`; «выполнена в N из M» — при трёх неделях в счёт и больше. Одно правило на обзор недели, месяц и год
- **Неделя принадлежит месяцу своего воскресенья** (Р-55) — для норм по неделям месяца. Время месяца — по дням месяца
- **План против факта** — по `plannedFor`; `doneOn` — день выполнения, и сделанное позже своего дня различимо. Удалённые пункты не считаются: надгробием уходят и пункты, снятые «Отменить» после шаблона (Р-44)
- **`someday`** — «когда-нибудь» из разбора висяков (Р-46): в неразобранном не лежит, у него свой блок на «Заметках». `dropped` не используется (Р-38, Р-44)
- **Наблюдение недели — обычная мысль**, обзор ссылается на неё `note:<id>` в `refs`; `Review.note` не используется (Р-49)

## Раскладка данных в репозитории

```
meta.json                 { schemaVersion }
categories.json           категории учёта времени
presets.json              кнопки быстрого ввода
templates.json            шаблоны дня
notes/2026-09.json        записи за месяц
notes/undated.json        записи без разбираемой даты (Р-08)
time/2026-02.json         блоки времени за месяц
reviews.json              обзоры недель
README.md                 что здесь лежит; кладётся приложением, если его нет (Р-69)
```

Месяц записи `Note` берётся по `capturedOn`, блока — по `date`. Даты нет — запись уезжает в `notes/undated.json`. Туда же попадает запись с испорченной датой: терять её из-за одной кривой строки нельзя.

Нарезка нужна git и сети. Без неё каждая отметка времени переписывала бы всю базу и раздувала историю коммитов. По месяцам, а не по годам (Р-28): годовой файл блоков к декабрю — около 440 КБ, и каждое нажатие отправляло бы его целиком; месячный — около 35 КБ. Закрытые месяцы не переписываются, пока в них ничего не правят.

Раскладка описана таблицей `places` в `src/app/config.ts` — единственное место, где она известна; файлы из неё собирает `layout` ядра. Правила самой раскладки — ключи, сортировка, `undated`, README — договор семьи.

## Синхронизация

**Принцип: local-first.** Запись сохраняется на устройстве и отражается на экране до всякой сети. Синхронизация — фоновый процесс, который может отставать или падать, не ломая работу.

Механика — ядра, `createSync` (Р-83); родом она из «Дневников» (Р-11). Три отличия от «Дневников», найденные здесь, живут теперь в ядре у всей семьи: нарезка по месяцам (Р-28); исправление в `syncNow` — проход отпускается и тогда, когда синхронизация не настроена (Журнал, Этап 2); `README.md` кладётся проходом, если его нет в дереве, и не трогается, если есть (Р-69). Шаги прохода:

1. Запись падает в IndexedDB, экран обновляется мгновенно
2. Изменённые записи помечаются грязными — это признак «есть что отправлять», а не список файлов
3. Через пять секунд после последнего действия — проход. Также при открытии, при возврате вкладки из фона и при возврате сети
4. Читаем голову ветки и дерево файлов — два запроса. Скачиваем только файлы с разошедшимся отпечатком
5. Сливаем в базу, пересобираем дерево из базы целиком, отправляем разошедшиеся **одним коммитом**
6. Ветка ушла вперёд → пауза, перечитать, слить заново. Три попытки, потом откладываем на минуту
7. **Сначала влить чужое, потом отправить своё.** Любая ошибка чтения обрывает проход до записи

Репозиторий без единого коммита Git Data API не обслуживает: первый файл кладётся через Contents API.

### Правило слияния

**Для каждой записи по `id` побеждает версия с более поздним `updatedAt`.** По записи, а не по файлу целиком — иначе запись с телефона затрёт запись с компьютера. Удалённые остаются надгробиями навсегда: вычистишь — второе устройство воскресит.

### Файл-копия

Кнопкой в «Настройках» скачивается один файл-слепок, а не раскладка выше:

```
{ schemaVersion, exportedAt, data: { <хранилище>: [записи] } }
```

Все синхронизируемые хранилища вместе с надгробиями. `settings` не входит — там токен. Загрузка сливается общим правилом. Форма проверяется до записи, файл чужой схемы отвергается целиком. Форма слепка — договор семьи.

Делимся `.txt` с тем же содержимым: Chrome на Android не отдаёт `.json` в системное «Поделиться».

### Импорт записей

Второй вход, для чужих записей — заметок Obsidian, февральской таблицы, выгрузок (Р-08). Слепок сюда не принимается, у него свой вход.

```
{ "format": "deluvremya-import", "version": 1,
  "notes": [...], "time": [...] }
```

Без `id` и `updatedAt`, ссылки по названиям: категория ищется по имени без учёта регистра, недостающая заводится.

- **Дата необязательна.** Запись без даты принимается, уезжает в `notes/undated.json`, видна в списке и в поиске — но в возврат наблюдений не попадает: показывать «месяц назад» нечего
- **Раздел `notes`** — `text`, `kind` (`task`, `thought`, `goal`; нет — дело, Р-13) и `date`. Дата — только днём: у заметки нет даты-месяца, и первое число было бы выдумкой. Известен только месяц — дата не пишется, запись ложится без даты; `ГГГГ-ММ`, кривая и будущая дата — в отчёт с причиной. Всё загруженное — открытым и не в плане
- Каждое поле проверяется; кривая запись в базу не попадает и называется с причиной
- До записи — сводка: что добавится, что уже есть, что не разобрано. Пишется только по кнопке
- **Только добавляет.** Совпавшее по естественному ключу пропускается. Ключи: заметка — текст и `capturedOn`; блок времени — категория, дата и минуты. Отсюда граница: два настоящих одинаковых блока в один день — «чтение 30» утром и вечером — импорт склеит в один. Для таблицы, где за день стоит сумма по занятию, это верно; для дневника с повторами занятий — нет, и тогда их надо сложить до импорта
- JSON принимается и в блоке ` ```json ` с текстом вокруг — так его отдаёт ИИ

Поля и пример каждого раздела описаны в `modules/<имя>/import.ts`; из тех же описаний собирается промпт для ИИ, и тест прогоняет примеры из промпта через собственную проверку. Разойтись они не могут. Механика разбора, сводка и общие правила промпта — ядра; свои правила промпта (даты, месяц без числа, минуты, таблица по дням) — `promptRules` в `app/config.ts`.

## Локальное хранилище

IndexedDB, не localStorage: у второго лимит около 5 МБ и синхронный API, который подвесит интерфейс на импорте.

База называется `deluvremya` (`dbName` в `app/config.ts`). Имя обязано отличаться от `dnevniki`: оба приложения живут на одном origin `goigolden88.github.io`, а IndexedDB общая на origin и различается только именем. Кеши service worker разведены сами — workbox вписывает scope в имя кеша и чистит только свой.

Синхронизируемые хранилища — `categories`, `presets`, `templates`, `notes`, `time`, `reviews`: имена совпадают с раскладкой в репозитории. Локальные — `meta`, `settings`, `dirty`. Имена лежат в базе на устройствах и не меняются никогда. Индексы сверх `updatedAt`: у `notes` — `capturedOn` и `plannedFor`, у `time` — `date`, у `reviews` — `weekStart`. Локальные хранилища одинаковы у всей семьи и заводятся ядром. `v1Stores` и `indexes` конфига заморожены с первым релизом: новое хранилище или индекс — только миграцией (Я-08 «FamilyCore»).

Настройки хранятся отдельно и **не синхронизируются**: в них токен, а «когда я в последний раз синхронизировался» у каждого устройства своё.

| Ключ | Что лежит |
|---|---|
| `syncEnabled` | включена ли синхронизация. По умолчанию нет |
| `syncRepo` | `владелец/репозиторий` данных |
| `syncToken` | fine-grained токен. В выгрузку не попадает никогда |
| `syncBranch` | ветка, по умолчанию `main` |
| `syncTokenExpires` | когда истекает токен |
| `syncLastAt`, `syncLastCommit`, `syncTree` | состояние последнего успешного прохода |
| `lastExportAt` | когда в последний раз забирали копию файлом |

Обзор недели читает оба модуля и потому модулем быть не может: он лежит в `screens/`, рядом с `app.tsx`, — иначе нарушил бы правило «модули не знают друг про друга» в первый же день.

**Ядро — `FamilyCore`** (Р-83): эталон один на всю семью, отсюда только читается. **Номера решений** (Р-85). Голый «Р-NN» в своих файлах — решение «Делу Время». В `src/shared` у каждой ссылки хозяин — «Р-11 „Делу Время“», «Р-32 „Дневников“», «Р-47 „Трапезы“», свои решения ядра — «Я-NN».

**Правила, которые соблюдаются жёстко:**

- Ядро не знает про приложение; `core` не знает про модули
- Модули не знают друг про друга — только через `refs` и общую ленту
- `ui` не знает про модули; модули пользуются `ui`
- Все модули разом знают только `app.tsx`, `registry.ts`, `notify.ts` и `screens/`
- К хранилищу обращаются только через `db` из `app/core.ts`, напрямую в IndexedDB не ходит никто, кроме `shared/core/db.ts`
- Работа с GitHub спрятана в ядре. Другой git-хостинг — правка ядра, для всей семьи
- Логика вне компонентов: расчёт — чистые функции с тестами, экраны тестами не покрываются

## Приём из «Поделиться» и быстрые действия

`share_target` в манифесте — `GET` на корень приложения с параметрами `title`, `text`, `url` (Р-16). Android открывает `/DeluVremya/?text=…`; `src/launch.ts` при старте, до первого экрана, переводит адрес во внутренний `#/inbox?shared=…` и чистит строку адреса. Service worker в приёме не участвует: такую навигацию он и так отдаёт из кеша, а без него её отдаёт GitHub Pages. Ссылка или кусок текста из любого приложения попадают во входящие без открытия экрана вручную — это прямая замена «Избранному» Телеграма. Картинки не принимаются — отложены (Р-16).

`shortcuts` в манифесте дают по долгому тапу на иконке: «Записать» (`?go=inbox`), «План дня» (корень), «Учесть время» (`?go=time`). Вход тот же, `launch.ts`. Адреса ярлыков и `share_target` зашиваются в установленное приложение на Android, поэтому меняются только вместе с обратной совместимостью: старый адрес обязан продолжать работать.

Оба механизма — Android у установленного приложения. На компьютере и во вкладке их нет, и это приемлемо: быстрый захват нужен с телефона.

## Как добавить модуль

1. **`app/model.ts`** — типы записей, имена хранилищ в `SYNCED_STORES`, строки в `StoreRecord`, новое значение в `RecordKind`
2. **`app/config.ts`** — строки в `indexes`, `places` (одним файлом или по месяцам, и по какой дате берётся месяц) и `storeNotes`. `v1Stores` не трогается никогда; индексы нового хранилища в `indexes` только держат таблицу полной — заводит их миграция
3. **`app/model.ts`** — миграция: поднять `SCHEMA_VERSION`, добавить шаг. Шаг **сам создаёт хранилище и его индексы**. `additive: true`, если форма прежних записей не меняется. Перед пушем — оба прогона на свежей копии настоящих данных. Первая миграция — точка невозврата перевода на ядро (Р-83)
4. **`modules/<имя>/`** — расчёт, экраны, работа с `db`. Логика модуля живёт здесь, а не в ядре
5. **`app.tsx`** — маршрут, при необходимости вкладка
6. **`src/registry.ts`** — строка на вид записи: подпись, строки ленты, раздел markdown, раздел импорта. Компилятор не соберёт приложение, пока строки нет

Чего делать **не** нужно: править ядро, проход синхронизации или соседний модуль. Понадобилось — граница нарушена, и это повод остановиться; нехватка ядра — сессией `FamilyCore`.

## Реестр видов записей

Общая лента и выгрузка в markdown — единственные места, где модули встречаются по данным. Реестр — таблица `{ [K in RecordKind]: … }` в `src/registry.ts`. Тип проверяется компилятором на полноту: забыть вид нельзя.

Маршруты, вкладки и блоки «Сегодня» через реестр не идут — это продуктовые решения, из списка они не выводятся.

Реестр рос по этапам (Р-23): с Этапа 1 — подпись и раздел импорта, с Этапа 6 — строки ленты и раздел markdown (Р-63). Раздел markdown принимает период и сам отбирает свои записи по своей дате; разделы в выгрузку выбирает человек (Р-79). Раздел импорта у вида необязателен: обзор недели не импортируется. Строки обзора — из `screens/reviewFeed.ts`: обзор не модуль (Р-60).

Лента читает слепок базы и перечитывает его на любое изменение. Правила строк:

- **Учёт** — строка на день, а не на блок; тап — день на экране учёта (Р-58)
- **Заметка** — в дне `capturedOn`, подпись — вид и состояние; без даты — внизу, группой «Без даты». Тап открывает карточку на «Заметках» — только у неразобранного и замысла; лента не правит (Р-59)
- **Обзор** — днём проведения, под ним наблюдение недели (Р-60)

Поиск ленты и «Заметок» — одно правило ядра: слова в любом порядке, регистр и «ё» не в счёт, дата и цифрами, и словами (Р-61).

## Версионирование схемы

`meta.json` содержит `schemaVersion`. Заводится с первого дня, миграции пишутся сразу: свежая база доезжает до текущей версии теми же шагами, что и база установленной копии. Отставание схемы само по себе не отвергает файл-копию — только если между версиями есть шаг с `additive: false`.
